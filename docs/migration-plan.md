# 数据库迁移方案（草案）

## 1. 当前数据库选择

当前部署只有一台 Rock Pi 3A、一个服务进程和 eMMC 存储，数据库读写量也不大，SQLite 是合适的选择。暂不引入 PostgreSQL，也不把数据库目录放到 WebDAV 或其他网络文件系统上。

运行约束：

1. 只运行一个 Uvicorn worker；Scheduler 和 Call Worker 不得再启动第二个进程写同一个库。
2. SQLite 开启 WAL、外键约束、busy timeout；批量写入使用短事务并由 SQLite 串行化写入。
3. eMMC 比 microSD 稳定，但仍需考虑断电损坏，重要操作前应保留备份。
4. 未来若出现多进程、多实例或明显写入瓶颈，再评估 PostgreSQL；这不是当前开发前置条件。

## 2. 迁移工具与原则

现在引入 Alembic。生产启动不再依赖 `create_all` 自动变更结构；每次结构变化都有可审查、可回滚的版本。

现有 `data/app.db` 只有开发数据，不做业务数据迁移。开发阶段创建全新的数据库和正式 schema；旧库只在切换前做归档备份，不删除。新 schema 仍保留回访相关表，并同时加入用户权限、业务台账、设备、联系人、字典、变更申请、暂存导入和审计表。

## 3. 具体步骤

1. 停止 Web、Scheduler 和 Worker，复制当前 `data/app.db`，并校验备份可读取。
2. 引入 Alembic，建立新 schema 的初始版本；开发数据库直接执行 `upgrade head`。
3. 新库先只建表和字典，不导入 Excel。
4. Excel 导入暂存表，生成字段映射、重复、格式和缺项报告。
5. 由业务/网络稽核人员审核导入批次；通过后分事务写入正式表，并保留原始行号和批次号。
6. 上线前执行业务号码、设备关联、缺项报告和恢复演练。

## 4. WebDAV 备份

可以定期将 SQLite 备份上传到 WebDAV，但不能直接上传正在写入的 `app.db`。备份任务应在本地先生成一致性快照，再上传临时文件，校验成功后原子改名。

- 使用 SQLite 在线 backup API 或 `VACUUM INTO` 生成快照。
- 上传到 HTTPS WebDAV，凭据只放在 `.env` 或系统密钥存储中。
- 建议对备份文件加密，再上传；保留日期、schema 版本和 SHA-256 清单。
- 保留本地滚动备份和 WebDAV 多个历史版本，失败时重试但不阻塞 Web 或拨号。
- 定期在临时目录恢复并执行完整性检查，确认备份确实可用。

## 5. 备份与失败处理

- SQLite 至少每日备份，导入批次、schema 迁移和批量作废前额外备份。
- 迁移失败时保留原 SQLite，不覆盖原文件；回滚通过切回旧服务和旧数据库完成。
- 迁移脚本不得删除原始导入文件、暂存行或审计记录。

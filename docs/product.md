# 产品与范围基线

本文是当前产品定位、数据、权限和 Web 交互的权威基线。文中“已实现”表示
当前代码和页面已经提供；“规划中”表示明确预留但尚未实现。硬件、串口、
通话状态和音频细节见 [`hardware.md`](hardware.md)。开发历史见
[`changelog.md`](changelog.md)。

## 1. 产品定位与范围

本系统是运行在 Rock Pi 3A 上的内网**运营支撑助手**。电话和短信的接收者是运维工作人员，不是客户本人：

- 到期维系：扫描协议到期窗口，通知客户经理办理续签或退网。
- 设备回收：扫描退网业务下未回收的设备，通知网络维护责任人回收。
- 审核卡单：扫描处于 `submitted` 的变更申请，通知有审核权限的人员处理。

通知任务由 `scan_schedules` 按每日/每周 cron 自动生成，管理员不再为客户手动
设置回访计划。电话使用 A7670E 单通道和本机音频播放；扫描配置可同时生成
A7670E 短信，短信与语音由 Worker 串行处理。话术是固定模板加数据占位符渲染
后的快照。

当前系统是内网运营工具，不提供实时 AI 对话、录音、ASR、DTMF 或公网安全能力。

## 2. 数据模型基线（已实现）

### 2.1 三层数据原则

Excel 是交换来源，不是最终数据库结构。数据分为三层：

1. **暂存层**：导入批次、原始行、列映射、校验结果和人工更正。
2. **正式层**：当前有效的规范化业务、设备、客户和联系人数据。
3. **历史层**：变更前后值、版本、操作者、审核者、时间和审计事件。

基线要求正式数据变更能追溯到变更申请或导入批次，版本冲突不得覆盖他人的
更新。导入和 `/daily-renewals`、`/daily-recycles` 已遵守该链路；`/ledger`、`/devices` 仍保留直接录入
表单，是“编辑草稿再提交”落地前的已知例外。

### 2.2 客户、联系人和扫描

- `customers` 保存客户主体。客户名称不是业务实例唯一键；客户随台账导入审核应用自动创建，
  业务录入时直接填写客户名称也会按名复用或自动创建（与字典字段同一交互语义）。
- `contacts` 是独立通讯录，保存姓名、电话、职责和有效状态。
- `customer_contacts` 保存客户主体与联系人的职责关联和导入追溯关系，不是通讯录录入入口。职责包括发展人、客户经理、网络维护责任人和客户；通知扫描只选择相应的工作人员职责。
- `scan_schedules` 取代手动 `callback_plans`，支持 `due_renewal`、`device_recycle`、`review_stuck` 三类扫描、cron、时区、提前天数、启停、话术和短信开关。
- `callback_plans` 仅为历史追溯保留，无页面入口。
- `call_tasks` 保留可空的历史 `plan_id`，并包含 `scan_schedule_id`、`source` 和
  `meta_json`。`source` 区分 `due_renewal`、`device_recycle`、`review_stuck`、
  `manual`、`scheduled`；`meta_json` 保存业务/设备目标、扫描配置和渲染话术
  快照，用于同日去重和追踪。

三类扫描按“同日同目标”去重。续签、退网申请从「客户维系登记」提交，设备
回收申请从「设备回收登记」提交；既有 POST 路径继续使用 `/due-work` 前缀
（历史路径兼容），审核应用后相应扫描窗口自然失效。

### 2.3 业务与设备

- `business_services` 是业务实例，业务号码 `service_number` 唯一；关联 `customers`，保存县分、网格、服务状态、入网时间、协议到期时间、业务类型、渠道、来源行、数据质量、版本和启用状态。
- `network_devices` 与业务实例是一对多关系，`device_code` 全局唯一；保存资产类别/价值、设备类型、厂商型号、位置、回收状态/原因、网络维护联系人、版本和启用状态。
- 字典表保存县分、网格、业务类型、服务状态、设备属性、设备类型、回收状态和回收原因等可停用枚举，避免同义词泛滥。

### 2.4 用户、变更与审计

- `users` 使用 `real_name`、`phone` 作为通知所需的实名和手机信息。系统管理员
  可不填手机；导入应用按职责自动建号，用户名为手机号，随机初始密码，首次
  登录强制改密，`auto_provisioned` 和 `force_password_change` 标识该状态。
- `change_sets` 表示人工提交或一次导入批次，`change_items` 表示新增、修改、作废及字段级 patch，并记录 `base_version`。
- 审核状态为 `draft`、`submitted`、`returned`、`approved`、`rejected`、`applied`、`cancelled`。
- `audit_logs` 记录登录、查询/导出、变更、审核、拨号、配置和管理员覆盖操作。

作废采用软删除，历史通话和审计记录不会随主体作废而消失。

导入流程是 XLSX 暂存 → 阻断/缺项/冲突校验 → 暂存行更正并重校验 → 业务域与
网络域分别审核 → 事务应用。导出为中文 `业务设备台账` 扁平工作表，每行是一条
业务与一台设备的关联；另含中文填写说明、枚举校验列、稳定 ID 和版本。版本
变化时报告冲突，不覆盖正式数据。

兼容旧台账时，设备编码按顿号、中文/英文逗号、中文/英文分号或换行拆分，每个
编码形成一条设备记录并继承该行其他设备字段；斜杠和竖线不作为合法分隔符。
设备编码跨业务重复、联系人无法匹配或同一业务行存在冲突值时进入异常清单。
只有业务域和网络域申请都审核并应用后，导入批次才标记为 `applied`。

当前集成样本为 3,113 行，历史验证得到 317 行阻断、2,796 行缺项和 107 个设备
归属冲突。原始 Q 列有 1,457 个非空单元格，其中 9 个用顿号或换行填写多个设备
编码；拆分后共 1,467 个编码，107 个编码跨两条业务出现，必须人工确认归属后
才能应用。协议到期时间、客户经理、网络维护责任人、设备属性、资产价格和
放置地点等历史样本字段大量缺失，“未回收原因”还混有状态描述，应报告为缺项
或语义异常。人工演练待办见 [`TODO.md`](../TODO.md)，字段和表头规则见
[`import-guide.md`](import-guide.md)。

## 3. 权限与审核流程（已实现）

权限按五个数据域（`business`、`network`、`callback`、`template`、`system`）与权限代码组合：

`read`、`create_draft`、`update_draft`、`delete_draft`、`submit`、`review`、
`apply`、`import`、`export`、`call_now`、`manage_users`、`manage_config`。

预置五个岗位模板：

| 岗位 | 默认职责 |
| --- | --- |
| 业务维护人 | business 域查询、草稿、新增/修改/作废申请、提交 |
| 业务稽核人 | business 域查询、审核、退回、应用 |
| 网络维护人 | network 域查询、草稿、新增/修改/作废申请、提交 |
| 网络稽核人 | network 域查询、审核、退回、应用 |
| 系统管理员 | 用户、角色、配置、导入导出、业务/网络审核应用和审计查看 |

新增、修改和作废统一形成变更申请；提交后进入审核中心，退回必须填写原因，
审核通过后在事务中应用。审核时检查 `base_version`，冲突要求重新合并。系统
管理员自提交自审核必须勾选二次确认，普通审核人不能审核自己的提交。审核通过
后仍要单独点击应用；两步均写审计日志。普通维护人员不能改写或删除通话事件。

用户不能自助注册，只能由超级管理员创建、启停和赋权。手机号和联系人电话在列表、日志和 `/sms` 页面默认脱敏。

## 4. Web 交互基线

### 4.1 已实现

- 本地 CSS 和少量原生 JavaScript，无 CDN；深色侧边栏包含工作台，以及数据
  管理、日常运维、回访与通话、系统管理四个清晰分组。
- 工作台展示待审核、缺项、到期业务、当前 Worker/拨号状态和近期异常。
- 业务台账、网络设备、通讯录、话术、扫描通知、审核中心、缺项工作台、导入
  导出、客户维系登记、设备回收登记、通话记录、短信通知、系统监控、备份与
  灾备、用户管理和角色权限页面均有入口。
- 业务台账支持业务号码/客户名称搜索和县分、服务状态筛选；网络设备支持设备
  编码/厂家型号搜索和回收状态筛选；审核中心支持状态筛选。通话记录支持筛选
  分页，详情页展示事件时间线。
- `/ledger`、`/devices` 当前提供直接新增、编辑和软删除表单，尚未改成“草稿 →
  提交 → 审核”交互。
- `/daily-renewals` 提供续签、退网申请（客户维系登记），`/daily-recycles`
  提供设备回收申请（设备回收登记），均显示同日通知和申请状态；已有未应用
  申请时防止重复提交。裸 `/due-work` 重定向到客户维系登记。
- `/scan-schedules` 配置三类扫描的 cron、时区、提前天数、话术和短信开关；不再提供客户级手动回访计划。
- 导入暂存行支持按业务/设备域更正并重新校验；字典和联系人字段支持输入补全与自定义值，系统稳定性校验字段只读。
- `/tasks/{id}/requeue` 支持人工重新入队；通话列表和详情保留未接通分类、分页、事件时间线及人工反馈补录。备份页支持本地快照、打包、WebDAV 上传、保留期管理、手动触发、下载和历史查看。
- 话术支持 `edge`/`none` Provider、命名缓存、`tts_error`、重试和页面试听；音频规范见 [`hardware.md`](hardware.md)。

### 4.2 规划中（尚未实现）

- 立即拨打一次的页面入口（服务层 `create_manual_call_task` 已存在，但没有路由）。
- 业务/设备详情抽屉的五页签、列分组切换、服务端分页、列显示选择和可保存筛选视图。
- 网格、业务类型、维护责任人、缺项和变更状态等完整台账筛选。
- 按权限分级展示手机号（当前统一脱敏）。
- 编辑草稿后再次提交、设备明细子表编辑、作废影响提示与理由确认。
- 审核逐字段接受和批量审核。
- 通话页突出未接通和有效时长不足 10 秒的记录。
- 备份加密上传。

规划项必须保持“规划中”标识，不能在后续协作中当作现状。

## 5. 系统与通知现状（已实现）

- Web、APScheduler 和可选 Call Worker 在一个 uvicorn 进程中运行；
  `CALL_WORKER_ENABLED=0` 默认关闭，管理页还有运行时开关。Scheduler 只生成
  任务，Worker 独占串口和音频。
- Worker 单通道执行语音和短信；短信受 `SMS_ENABLED=1` 和扫描配置 `sms_enabled` 双重控制，失败记录到 `sms_notifications`，不阻塞语音。`/sms` 展示最近 200 条脱敏记录。
- 通话使用 `CALL_STATUSES` 的 11 个主状态，所有串口收发、URC、状态变化、播放开始/结束和错误逐条写入 `CallEvent`；细节见 [`hardware.md`](hardware.md)。
- `/admin/system` 提供 status/logs/settings 三个视图，展示 Worker、调度器和运行日志；应用启动时校验 Alembic schema 版本。
- SQLite 结构由 Alembic 管理，启动只校验 schema 版本；备份打包 SQLite 一致性快照、`data/imports/` 和 `data/audio/`，本地保留并可上传 WebDAV。

## 6. 明确延期范围

- ASR、录音、实时转写、LLM 实时对话、抢断、动态话术和 DTMF。
- 节假日/工作日历和复杂补偿策略。
- 运营商短信网关、邮件、企微等外部通知通道（A7670E 直发短信已实现）。
- 备份加密上传。
- 公网部署安全加固；当前多用户、角色和业务域权限只按内网工具定位。
